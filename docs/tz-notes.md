# Аналіз технічного завдання проєкту Student Assistant

## 1. Функціональні вимоги

Student Assistant --- це навчальний застосунок для керування
студентськими завданнями. Основне призначення системи --- допомогти
студенту організовувати навчальний процес, контролювати терміни
виконання та визначати пріоритетність завдань.

Система повинна забезпечувати такі можливості:

-   Перегляд повного списку навчальних завдань.
-   Додавання нових завдань із зазначенням назви, дедлайну та
    пріоритету.
-   Редагування інформації про наявні завдання.
-   Видалення непотрібних завдань.
-   Позначення завдань як виконаних або невиконаних.
-   Визначення пріоритету кожного завдання: низький, середній або
    високий.
-   Фільтрація та сортування завдань за станом виконання або
    пріоритетом.

Усі клієнтські модулі повинні реалізовувати спільний мінімальний набір
функцій, щоб користувач міг працювати зі своїми завданнями незалежно від
обраної платформи.

## 2. Нефункціональні вимоги

До системи висуваються такі нефункціональні вимоги:

-   **Кросплатформність:** сукупність клієнтських модулів повинна
    забезпечувати роботу на Windows, macOS та Linux.
-   **Незалежність модулів:** кожен клієнт повинен бути самостійним
    компонентом і не мати прямих залежностей від інших клієнтів.
-   **Спільний формат даних:** усі модулі повинні використовувати єдиний
    файл `data/tasks.json`.
-   **Сумісність:** клієнти повинні правильно читати та обробляти
    спільну структуру даних.
-   **Розширюваність:** архітектура повинна дозволяти розвивати окремі
    модулі без необхідності повністю переробляти інші.
-   **Контроль версій:** розробка повинна здійснюватися за допомогою Git
    і GitHub із використанням окремих гілок, Pull Request та
    рецензування коду.
-   **Документування:** репозиторій повинен містити `README.md` з описом
    проєкту та `docs/tz-notes.md` з аналізом технічного завдання.

## 3. Модулі та технології

Проєкт складається з чотирьох незалежних клієнтських модулів.

  -----------------------------------------------------------------------
  Модуль                  Технологія              Призначення
  ----------------------- ----------------------- -----------------------
  Вебклієнт               React                   Робота із завданнями
                                                  через вебінтерфейс

  Десктопний контейнер    Electron або NW.js      Запуск вебінтерфейсу як
                                                  настільного застосунку

  Нативний десктопний     C++ / Qt                Робота із завданнями
  клієнт                                          через нативний
                                                  інтерфейс

  Аналітичний модуль      Python / Flet           Робота з даними та їх
                                                  аналітичне
                                                  представлення
  -----------------------------------------------------------------------

Усі модулі повинні бути незалежними один від одного та використовувати
спільний файл `data/tasks.json`.

Кожен модуль реалізує власний інтерфейс і відповідний архітектурний
підхід кросплатформності.

## 4. Формат обміну даними

Для обміну інформацією між клієнтськими модулями використовується
спільний файл `data/tasks.json` у форматі JSON.

Кожне завдання представлене окремим об'єктом із такими властивостями:

  Поле          Тип даних   Призначення
  ------------- ----------- ----------------------------------------
  `id`          Числовий    Унікальний ідентифікатор завдання
  `title`       Рядок       Назва завдання
  `completed`   Логічний    Стан виконання: `true` або `false`
  `dueDate`     Рядок       Дата завершення у форматі `YYYY-MM-DD`
  `priority`    Рядок       Пріоритет: `low`, `medium` або `high`

Приклад запису:

``` json
{
  "id": 1,
  "title": "Підготувати конспект лекції",
  "completed": false,
  "dueDate": "2026-09-15",
  "priority": "medium"
}
```

Основні правила роботи з даними:

-   Ідентифікатор кожного завдання повинен бути унікальним.
-   Поле `completed` повинно містити логічне значення.
-   Дата повинна відповідати формату `YYYY-MM-DD`.
-   Пріоритет повинен приймати лише одне з трьох визначених значень.
-   Усі клієнти повинні дотримуватися єдиної структури JSON.
-   Зміна складу або призначення полів допускається лише після
    узгодження та документування в `README.md`.

## 5. Відкриті питання

Під час аналізу технічного завдання виникають питання, які доцільно
уточнити у викладача перед початком повноцінної розробки:

1.  Як саме повинна відбуватися синхронізація змін між клієнтськими
    модулями, якщо кілька програм одночасно працюють зі спільним файлом
    `tasks.json`?
2.  Чи потрібно передбачити механізм резервного копіювання даних у разі
    пошкодження JSON-файлу?
3.  Чи повинна система підтримувати кілька користувачів або
    передбачається використання одним студентом?
4.  Чи необхідно реалізувати перевірку правильності введення дат, назв
    та пріоритетів на рівні кожного клієнта?
5.  Чи передбачається збереження історії змін навчальних завдань?
6.  Які саме можливості аналітики повинні бути реалізовані в модулі
    Python / Flet?
7.  Чи є конкретні вимоги до дизайну та адаптивності вебінтерфейсу?
8.  Які критерії продуктивності та швидкості роботи повинні виконувати
    клієнтські модулі?

## Висновок

У результаті аналізу технічного завдання визначено призначення, основні
функціональні можливості, архітектуру та технології майбутнього проєкту
Student Assistant.

Система повинна складатися з чотирьох незалежних клієнтських модулів,
які працюють зі спільним форматом даних JSON. Такий підхід дозволяє
використовувати різні технології для створення інтерфейсів, зберігаючи
єдину структуру інформації.

Визначені вимоги та відкриті питання стануть основою для подальшого
проєктування, розробки й інтеграційного тестування системи.
